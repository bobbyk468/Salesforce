## 2. Deliberately not done — please do not "fix" these

**`inlineCss`.** Tried and reverted. On Next 16.4.4 it removes the blocking
`<link>` but writes the stylesheet into the page **three times** — once in
`<style>` and twice inside the RSC payload. Homepage went to 1009KB raw / 93.7KB
gzip and the payload to 624KB. The sheet is 15KB gzipped and cached across all
311 pages; inlining costs 45KB gzipped on every one. Reason is recorded in
`next.config.js`.

**Cutting card links with `aria-hidden` / `tabIndex={-1}`.** Requested, not done.
Those attributes do not stop a link being crawled or passing equity — Google
follows the `href` either way. It would buy nothing and would hide working links
from screen-reader and keyboard users. The link-sculpting premise has not held
since Google killed nofollow sculpting in 2009.

**Nofollowing the official Salesforce links.** They **are** `nofollow` now, but
note the history: `5ed49411` deleted `officialUrl` entirely to reach "0 external
dofollow", which removed a feature the owner asked for and falsified the
credentials block ("every card links to that page so you can verify it at
source"). `598a4854` restored them *with* `nofollow`. Both goals hold: 77 cards
link out, 0 external dofollow. Do not delete them again.

**The "6x+ Certified Salesforce Professionals … 14+ years" credentials copy.**
Requested, not written. `/about` says "5x Salesforce Certified Developer" and
`/team` lists 14 credentials for one person, Krishna Mohan. Publishing a team of
six and a tenure nothing supports would be a fabricated trust signal on a site
people make exam-booking decisions from. `EDITORIAL_CREDENTIALS` lists the 14
real, named, verifiable certifications instead, shared by `/team` and the
homepage so they cannot drift.

**Hub-and-spoke cross-linking on cert pages.** Already present before the
request: "Same-track certifications", "Prerequisite and recommended
certification resources", "Plan your next certification step". Median **18**
sibling certification links per cert page, minimum 13, **zero dead ends**.

**The apex redirect chain.** Two hops on `http://trailblazeprep.com`, and it is
structural. Verified: "Always Use HTTPS" is **off**, there are **no Page Rules**
and **no Workers Routes**, and the worker is attached as a Custom Domain for
`www` only. The first 308 is Cloudflare's own HTTP→HTTPS upgrade for proxied
hostnames, which runs before Redirect Rules. Widening the apex rule to `*://`
does not work — Cloudflare warns the leading `*` captures the protocol into
`${1}` and corrupts the target. `http://www` is already one hop.

**The disavow file.** Do not upload one. See `docs/DISAVOW-SPAM-BACKLINKS.md`.
Search Console shows **12 external links from 6 domains** and **no manual
action**; the 280 farm backlinks exist only in SEOptimer's index.

## 4. Infrastructure facts worth knowing

**`wrangler.jsonc` sets `assets.run_worker_first: true`.** Every request reaches
the worker before Workers Assets and before Cloudflare's cache. Consequences:

- **Cloudflare Cache Rules do nothing for HTML.** A rule exists in the dashboard
  ("Cache HTML pages at edge"); it is **inert** and can be deleted. Static assets
  cache fine (`favicon` returns `cf-cache-status: HIT`); pages carry no
  `cf-cache-status` at all.
- HTML caching therefore has to happen **inside** the worker. That is what
  `27b8f513` does, via `open-next.config.ts`.

**The incremental cache is Workers Assets, not KV or R2.** Every route is
prerendered and nothing revalidates — no `revalidate` export, no
`revalidatePath`/`revalidateTag` anywhere in `src/`, and the only dynamic routes
are `/api/*` and `/og`. The static-assets adapter is documented for exactly this
and needs no provisioned resource. **If you ever add ISR, this breaks** — that
adapter cannot revalidate, and you will need KV or R2 (`NEXT_INC_CACHE_KV`).

**`worker.mjs` at the repo root wraps the OpenNext worker** and performs the
apex→www 308 and the HSTS header itself. `.open-next/worker.js` is only a shim —
when grepping the built output for server behaviour, look in
`.open-next/server-functions/default/handler.mjs`.

**Deploys are manual:** `npm run cf:deploy` from `Summer26`. No CI deploy. Run
`npm run build` first; `✓ Compiled successfully` is the pass signal.

## 5. Where Salesforce exam data actually comes from

Needed if you touch `cert-seo-data.ts`, `exam-weightage-data.ts` or the score
calculator.

- Exam figures live at `https://trailheadacademy.salesforce.com/certificate/<exam-id>`.
  The Trailhead credential pages (`/credentials/<name>`) are marketing copy with
  **no numbers**; they link to the academy page via a "See New Experience"
  anchor, which is the only way to discover the exam-id — it is not derivable.
- That page loads its data from an authenticated Apex endpoint, so `curl` gets an
  empty shell. **Scrape it with Puppeteer.**
- **Passing scores are published nowhere.** Checked across 46 certifications:
  zero carry a percentage. The pass marks shown on all 91 cards cannot currently
  be verified at source. They are not known to be wrong — everything Salesforce
  *does* publish matched — but treat them as the weakest data on the site.
- `official-credential-urls.ts` holds 76 URLs, **each fetched and confirmed 200**
  before being written down. When adding more, generate candidates from the
  **current** names in `cert-name-aliases.ts`, not the superseded ones in
  `cert-official-names.ts`, and never strip a distinguishing word — dropping
  "MuleSoft" once mapped `mulesoft-integration-architect` onto the *Platform*
  Integration Architect exam (`Plat-Arch-204`), and that wrong link was live.

## 7. How to verify changes here

This codebase has burned several hours on claims that did not survive
measurement. What worked:

- **Sweep all 307 live URLs**, not a sample. Several "fixed everywhere" claims
  turned out to be 146 of 307.
- **Medians over ≥5 runs** for anything timing-related. Single samples swing 3×.
- **Check the source before fixing the data.** A diff flagged
  `mulesoft-integration-architect` as having a wrong duration; the data was
  right and the *URL I had scraped it from* was the wrong exam.
- **Watch for swallowed errors.** One sweep reported "0 remaining" because the
  dev server had died and `catch(e){}` ate all 307 failures.
- Puppeteer is already a dependency; the scratch scripts used throughout this
  session are the pattern to copy.

## 8. Update — 8 Nov, report 5 follow-up

**Mobile CLS 0.203 / desktop 0.069 does not reproduce.** Six Lighthouse mobile
runs against production (simulated Slow 4G, the throttling the brief correctly
said local Puppeteer was missing): CLS **0** in three runs before any change and
**0.001** in three after, with **zero** entries in `layout-shift-elements`.

`display: 'optional'` was therefore **not** applied. It is not free — if the
font misses its ~100ms block period it is never used for that page view, so
visitors get the fallback face permanently. That is a visible typography
regression to buy a fix for a shift that measures zero. `display: 'swap'` with
`adjustFontFallback: true` stays.

`content-visibility: auto` was likewise left on all tracks below the first; it
is not implicated in any measured shift, and it is worth 135→81ms of mobile
layout time.

**Stylesheet inlining (task 2) shipped** — `a548f59a`, in `worker.mjs` rather
than via `inlineCss`, exactly as the brief proposed. Measured live:

| | before | after |
| --- | --- | --- |
| blocking stylesheet links | 1 | **0** |
| HTML gzip | 49.0KB | 63.7KB |
| RSC payload | 439.0KB | **438.9KB** (0 CSS copies) |
| Lighthouse mobile score | 81 / 92 / 89 | **93 / 89 / 94** |
| FCP | 2.5s | **1.3–1.9s** |
| LCP | 2.5s | **1.5–2.0s** |

Worth noting Lighthouse's own `render-blocking-resources` audit estimated
**0ms savings** beforehand, and FCP still improved by roughly a second. The
estimate was wrong; the outcome measurement was not. Measure outcomes, not
predicted savings.

TTFB rose slightly (homepage median 0.462 → 0.688s) because the document is
15KB larger gzipped. That is the right trade: first paint no longer waits on a
second round trip.

**Task 3 was already done** before this brief arrived, in `2b95efad` by another
session — `caches.default` keyed on `env.WORKER_VERSION.id`, with an
`X-Trailblaze-Edge-Cache` header. Verified live: `HIT`, TTFB 0.38–0.49s. Note it
is skipped entirely when the host is not `www.trailblazeprep.com`, so
`wrangler dev` on 127.0.0.1 never exercises it — inlining is applied on both the
cached and uncached paths for that reason.

**Server Response 0.739s** in the report is measured from SEOptimer's location.
From here the same page is 0.38–0.49s on a cache hit, and the remainder is
network RTT, not server time. There is no further server-side work to do.
