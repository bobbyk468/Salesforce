## 2. Deliberately not done — please do not "fix" these

**`inlineCss`.** Tried and reverted. On Next 16.4.4 it removes the blocking
`<link>` but writes the stylesheet into the page **three times** — once in
`<style>` and twice inside the RSC payload. Homepage went to 1009KB raw / 93.7KB
gzip and the payload to 624KB. The sheet is 15KB gzipped and cached across all
311 pages; inlining costs 45KB gzipped on every one. Reason is recorded in
`next.config.js`.

**Cutting card links with `aria-hidden` / `tabIndex={-1}`.** Requested, not done.
Those attributes do not stop a link being crawled or passing equity — Google
follows the `href` either way. It would buy nothing and would hide working links
from screen-reader and keyboard users. The link-sculpting premise has not held
since Google killed nofollow sculpting in 2009.

**Nofollowing the official Salesforce links.** They **are** `nofollow` now, but
note the history: `5ed49411` deleted `officialUrl` entirely to reach "0 external
dofollow", which removed a feature the owner asked for and falsified the
credentials block ("every card links to that page so you can verify it at
source"). `598a4854` restored them *with* `nofollow`. Both goals hold: 77 cards
link out, 0 external dofollow. Do not delete them again.

**The "6x+ Certified Salesforce Professionals … 14+ years" credentials copy.**
Requested, not written. `/about` says "5x Salesforce Certified Developer" and
`/team` lists 14 credentials for one person, Krishna Mohan. Publishing a team of
six and a tenure nothing supports would be a fabricated trust signal on a site
people make exam-booking decisions from. `EDITORIAL_CREDENTIALS` lists the 14
real, named, verifiable certifications instead, shared by `/team` and the
homepage so they cannot drift.

**Hub-and-spoke cross-linking on cert pages.** Already present before the
request: "Same-track certifications", "Prerequisite and recommended
certification resources", "Plan your next certification step". Median **18**
sibling certification links per cert page, minimum 13, **zero dead ends**.

**The apex redirect chain.** Two hops on `http://trailblazeprep.com`, and it is
structural. Verified: "Always Use HTTPS" is **off**, there are **no Page Rules**
and **no Workers Routes**, and the worker is attached as a Custom Domain for
`www` only. The first 308 is Cloudflare's own HTTP→HTTPS upgrade for proxied
hostnames, which runs before Redirect Rules. Widening the apex rule to `*://`
does not work — Cloudflare warns the leading `*` captures the protocol into
`${1}` and corrupts the target. `http://www` is already one hop.

**The disavow file.** Do not upload one. See `docs/DISAVOW-SPAM-BACKLINKS.md`.
Search Console shows **12 external links from 6 domains** and **no manual
action**; the 280 farm backlinks exist only in SEOptimer's index.

## 4. Infrastructure facts worth knowing

**`wrangler.jsonc` sets `assets.run_worker_first: true`.** Every request reaches
the worker before Workers Assets and before Cloudflare's cache. Consequences:

- **Cloudflare Cache Rules do nothing for HTML.** A rule exists in the dashboard
  ("Cache HTML pages at edge"); it is **inert** and can be deleted. Static assets
  cache fine (`favicon` returns `cf-cache-status: HIT`); pages carry no
  `cf-cache-status` at all.
- HTML caching therefore has to happen **inside** the worker. That is what
  `27b8f513` does, via `open-next.config.ts`.

**The incremental cache is Workers Assets, not KV or R2.** Every route is
prerendered and nothing revalidates — no `revalidate` export, no
`revalidatePath`/`revalidateTag` anywhere in `src/`, and the only dynamic routes
are `/api/*` and `/og`. The static-assets adapter is documented for exactly this
and needs no provisioned resource. **If you ever add ISR, this breaks** — that
adapter cannot revalidate, and you will need KV or R2 (`NEXT_INC_CACHE_KV`).

**`worker.mjs` at the repo root wraps the OpenNext worker** and performs the
apex→www 308 and the HSTS header itself. `.open-next/worker.js` is only a shim —
when grepping the built output for server behaviour, look in
`.open-next/server-functions/default/handler.mjs`.

**Deploys are manual:** `npm run cf:deploy` from `Summer26`. No CI deploy. Run
`npm run build` first; `✓ Compiled successfully` is the pass signal.

| desktop TBT | 300ms | 140ms |

### Three changes shipped

- `next/font` is `display: 'optional'`, not `'swap'` (`0bd3fe16`). A late font
  can no longer reflow the H1 or the jump-bar labels. `adjustFontFallback`
  stays on so the fallback is metrically close.
- The jump bar is a **fixed-column grid**, not `flex-wrap` (`0bd3fe16`). Its
  row count no longer depends on how wide the labels render, so no metric
  change can alter its height and push the tracks below it down.
- `.cv-auto` is **no longer used on the homepage** (`ede2071e`). It reserved
  600px per section while the real height on a narrow viewport is several
  times that, so each activation reflowed the page. Mobile TBT is now 50ms, so
  there was nothing left to buy. The class remains in `globals.css` for other
  pages, with a note to measure real heights per breakpoint before reusing it.

### What did not move, and the open question

**CLS stayed at exactly 0.203 mobile / 0.069 desktop across all three
deploys**, while TBT and the overall score moved freely in the same runs. A
genuine layout shift would vary at least slightly when the font strategy, the
nav's layout mode and `content-visibility` all change. It did not vary at all.

Locally, with Moto G Power emulation, real Slow 4G throttling (1.6Mbps,
150ms RTT) and 4x CPU — matching PSI's stated configuration — CLS measures
**0.0013**, and the only shifting element is a link in body copy.

So either PSI is caching the CLS metric separately from the rest of the run,
or it exercises something that this configuration does not. **Do not ship more
speculative CLS fixes against this number.** The next step, if it matters, is
to capture a PSI trace (`lighthouseResult.audits['layout-shift-elements']` plus
the trace artefact) and compare its screenshot timeline against a local run,
rather than changing code and re-measuring.

The three changes above are each defensible on their own merits and are worth
keeping regardless.

### The embed and X-Frame-Options

`next.config.js` sets `X-Frame-Options: DENY` on every route, which is right
everywhere except the embed. It **cannot** be relaxed per-route in
`next.config.js`: Next *appends* a repeated header key rather than replacing
it, so an override emits `DENY, ALLOWALL` and browsers treat a malformed
`X-Frame-Options` as a refusal.

So `worker.mjs` has `allowFramingIfEmbed()`, which on
`/tools/score-calculator/embed` deletes the header and appends
`frame-ancestors *` to the CSP (X-Frame-Options has no allow-list form;
`frame-ancestors` is the modern equivalent). It runs on all four exit paths —
cache HIT, cache MISS, uncached production, and non-production — and
deliberately **after** `cache.put`, so the cached object keeps the strict
header and the relaxation is applied per response.

Verify after deploy:

```bash
curl -sI https://www.trailblazeprep.com/tools/score-calculator/embed | grep -i 'frame\|content-security'
curl -sI https://www.trailblazeprep.com/certifications | grep -i 'x-frame'
```

The first must show no `x-frame-options` and a CSP containing
`frame-ancestors *`. The second must still show `DENY`. If the second ever
loses it, the route pattern has gone wrong — that is the regression to watch.

### Honest limit on the embed

**Links inside an iframe are not attributed to the host page.** The
attribution bar inside the embed is good manners and good for referral
traffic; it is not a backlink. The part that carries attribution is the credit
paragraph *outside* the iframe, which is why it is included in the copyable
snippet on `/tools/score-calculator` rather than suggested separately. Do not
report embed installs as link acquisition.

### Post-deploy audit of §11, and one correction

Three things were wrong on the first deploy and are fixed (`cff93fa1`):

- **The report page had no share cards of its own.** It inherited the site
  defaults, so it shared as "Free Salesforce Exam Practice Tests" with
  `og:url` pointing at the homepage — on the one page built to be shared.
- **Neither the report nor `/tools/score-calculator` was in `sitemap.xml`.**
  `sitemap.ts` is built from `public/urls.json`, a checked-in index; a new
  route is invisible to the sitemap until it is added there. The calculator
  had been missing since it shipped. **Add new indexable routes to
  `public/urls.json`.** The embed stays out: it is `noindex`.
- **`GoogleAnalytics` now bails on the embed route**, so our gtag can never
  run inside someone else's page.

**Correction to that last one.** It was reported as a live leak. It was not:
`NEXT_PUBLIC_GA_MEASUREMENT_ID` is set in no `.env` file, no `wrangler.jsonc`
var, and appears in no built chunk, so `GoogleAnalytics` returns null and
**gtag has never loaded anywhere on this site**. The guard is correct
future-proofing — the day someone sets that ID, the embed would start
reporting from third-party pages — but it fixed nothing that was happening.

The larger finding is the one underneath it: **the site collects no Google
Analytics data.** The loader, the preconnect hint and the CSP allowances for
googletagmanager are all in place around a measurement ID that does not
exist. Either set it or remove the scaffolding; leaving it is how the next
person loses another afternoon.

### Known and accepted, not bugs

- **Cloudflare Web Analytics does run inside the embed.** Cloudflare injects
  `static.cloudflareinsights.com/beacon.min.js` at the edge, after the worker,
  so `worker.mjs` cannot strip it. It is cookieless and does not track
  individuals, so it is a much smaller thing than gtag would have been, but
  host sites do get a beacon request. Turning it off is a dashboard setting
  that affects the whole site, so it is a judgement call, not a fix.
- **The embed ships the full site chrome in its HTML** — header, footer,
  sidebar and WhatsApp markup, hidden by CSS in the embed layout, ~206KB.
  Removing it properly needs multiple root layouts, which needs every route
  moved into a route group. Not worth it for one route; noted so nobody
  reports the hidden markup as a bug.
- **Framing verified end to end** by iframing the embed from `example.com`:
  it renders, so `allowFramingIfEmbed` works against a real third-party
  origin, not just in a header dump.
- The report page's tables are wider than anything else on the site, so the
  desktop contact sidebar crowds them. They scroll horizontally, nothing is
  unreachable, but this is the page where that layout shows first.

## 12. Update — report 7 follow-up: the PSI diagnosis that §10 was missing

§10 said CLS was frozen at 0.203 mobile / 0.069 desktop, unattributable, and
recommended capturing a PSI trace rather than shipping more guesses. That is
what happened here, and it produced answers.

### How to get live PSI data when the API is rate-limited

The anonymous PSI API has a per-day quota shared across all keyless callers,
and it was exhausted:

```
Quota exceeded for quota metric 'Queries' ... pagespeed.web.dev
```

**Use the web UI instead.** `https://pagespeed.web.dev/analysis?url=<encoded>&form_factor=desktop`
runs the same Lighthouse and exposes **both** form factors' complete
Lighthouse JSON on `window.__LIGHTHOUSE_DESKTOP_JSON__` and
`window.__LIGHTHOUSE_MOBILE_JSON__`. Read those in a browser console and you
have every audit the API would have given you, with no key and no quota.
Check `fetchTime` to be sure you are not reading a cached analysis.

### Read `layout-shifts`, not `layout-shift-elements`

This is why §10 concluded the shift was unattributable. The older
`layout-shift-elements` audit returns an **empty list** on these runs. The
newer `layout-shifts` audit, in the same report, names the element:

```
score 0.0694  →  section#certification-track-associate
```

The first certification track section, which means something above it changes
height after first paint. **Always check `layout-shifts` first.**

### CLS: the element is named, the cause is not, and the metric is unstable

Two PSI runs an hour apart, on two builds:

| | run A | run B |
| --- | --- | --- |
| desktop CLS | 0.069 | 0.069 |
| desktop element | `section#certification-track-associate` | same |
| mobile CLS | **0** | **0.203** |
| mobile element | — (no shift) | `nav.mb-10` (the jump bar) |

**Mobile CLS is intermittent.** It was 0 in run A and 0.203 in run B. Do not
read a single run as proof that a CLS change worked — that is the mistake this
section exists to prevent, and it nearly went into this document as "mobile
CLS went 0.203 → 0".

What is now established:

- **The element is named on both form factors.** Mobile blames the jump bar
  itself; desktop blames the first track section directly below it. Both are
  consistent with one thing above them changing height.
- **It is not the webfont.** Loading the live homepage with every `.woff2`
  request aborted gives *byte-identical* geometry at 412px: H1 144px, nav
  336px, first track at y=885 either way. `adjustFontFallback` is doing its
  job. Blaming the font — which §10 did, and which motivated
  `display: 'optional'` — is ruled out.
- **It does not reproduce locally**, at either form factor, under PSI's own
  stated configuration. Desktop (1350x940, 1x CPU, 10Mbps/40ms): **0.0019**.
  Mobile (412x823, DPR 1.75, 4x CPU, 1.6Mbps/150ms): **0.0013**, and every
  recorded shift source has an identical before and after rect.

So the next step is **not** another code change. It is the PSI trace itself —
`lighthouseResult.audits['screenshot-thumbnails']` and the trace artefact —
compared against a local run, to see what is on screen either side of the
shift. Everything cheaper than that has now been tried and written down.

### Two real bugs, both fixed

**1. `requestIdleCallback` was not a 20-second delay.**

```js
// Before — reads like "load after 20s", is not:
idleId = requestIdleCallback(load, { timeout: fallbackMs })
```

rIC fires as soon as the browser is **idle**; the timeout is only an upper
bound. A Lighthouse run is the quietest page there is, so it fired at ~2s and
put gtag inside the Total Blocking Time window. Measured cost on the live PSI
run: long tasks of **176ms and 159ms on mobile** (253ms of script evaluation,
344ms total) and **78ms + 71ms on desktop** — the largest single contributor
to mobile TBT of 420ms. Now a `setTimeout` that actually waits, with rIC used
only to pick a quiet moment afterwards. The interaction delay went 1s → 3s
because **Lighthouse scrolls the page**, which trips the interaction gate.

Verified after deploy: no gtag script 8 seconds after load.

**2. GA is live, and §11's correction was itself wrong.**

§11 said gtag "has never loaded anywhere on this site". That is false. It
loads on every page with measurement ID `G-QCZP88TZHG`, confirmed three ways:
in the live PSI network log, as a `#ga-config` element in the live DOM
carrying our own template verbatim, and inside the deployed chunk.

**Where the ID comes from is unresolved.** It is in no `.env` file, no
`wrangler.jsonc` var, no `.dev.vars`, not in `.next/cache`, and not in the
current local build output — yet it is compiled into the deployed chunk next
to our `NO_ANALYTICS_ROUTES` array, so that chunk is from today's build. That
means **builds here are not reproducible**: `npm run build` and
`npm run cf:deploy` are producing different bundles from the same source. Do
not spend time on the GA question without settling that first.

### The duplicate CSS, and why it stays

Report 7's "2 CSS resources" is real and still real. Confirmed on the live
page: two resource entries for the same `.css`, and one
`<link rel="stylesheet">` in the DOM although the served HTML contains none.

Adding `data-href` to the inlined `<style>` was tried, deployed and measured.
**It does not help.** Neither reference comes from the HTML:

```
:HL["/_next/static/chunks/<hash>.css","style"]      <- RSC preload hint
["$","link","0",{"rel":"stylesheet","href":...}]    <- React inserts this
```

Both live in the RSC flight payload. `HTMLRewriter` rewrites tags, not
serialized React state. Editing that payload would risk hydration for one
cacheable, off-critical-path request, and Next's `experimental.inlineCss`
removes both at the cost of writing the stylesheet three times (730KB →
1009KB raw, measured). **Inlining still does its job** — first paint is not
blocked — so the trade stands. There is no `Link: rel=preload` response
header; that part of the audit is clean.
